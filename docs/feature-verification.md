# Gergram feature verification

This register accounts for all 81 rows in the [feature audit](ayugram-feature-audit.md) against the [architecture review](architecture-review.md) and [development plan](development-plan.md). The review starts at fork checkpoint `4d421e15` and includes the incremental changes recorded below. The official macOS base is `ec221d85`. The final column gives the remaining acceptance criteria or release work.

**Implemented** means the source covers the supported scope in that row. **Partial** means a path exists and an audited behavior remains. **Native candidate** means the inherited implementation needs an equivalence check. **Planned** means the fork has no implementation for the requested behavior. **Dependency** identifies missing capability or data. **Release decision** means the architecture review reserves a behavior for a specific connected-release decision. A unit, fixture or parse result applies only to the code it ran.

## Verification boundaries

Recorded evidence is focused on individual source paths. The CLI dependency preflight and focused fixtures do not establish application startup, actual Telegram delivery, macOS accessibility or application-wide resource behavior. The [development plan](development-plan.md) records the integrated build blockers at the checkpoint, including unavailable pinned components and the Metal toolchain. The full launch and paired parity runs remain blocked. Instruments failed to connect to its recording service on this host, and the standalone leak utility could not obtain a task port.

For acceptance on a complete macOS build, run the two-account and permission-sensitive rows above with disposable accounts and synthetic media. Profile repeated open/close, seek/cancel, settings and account switch cycles with Allocations and Leaks, and run Address Sanitizer and Thread Sanitizer in separate builds where supported. Include capture toggles, story prefetch and reactions, received transcription, Message Shot, custom emoji preview and archive logout/cleanup. Verify release of windows, subscriptions, requests, temp files and database handles after each owner ends. Record actual app build, OS, hardware, timing, peak resident memory and any remaining allocations with each result.

For C33, run equal cold-cache and warm-cache scenarios at the same endpoint and network conditions, including two accounts, one foreground video and background transfers. Measure useful bytes per second, first decodable frame and seek latency, request count and retransmitted bytes, disk writes and peak resident memory. Compare against the unmodified fork baseline and record path, data center, file sizes and connection conditions.
