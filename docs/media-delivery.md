# Media delivery and streaming

**Decision.** Increase useful throughput by reducing redundant range work, prioritizing playback and measuring the existing transport. Telegram provides per-DC file concurrency settings, request alignment rules and flood-wait responses. Server-provided entitlement and DC limits, link capacity, CPU and disk throughput bound delivered speed. Treat a faster client as one that reaches the available goodput with lower startup and seek latency. Preserve existing proxy, authorization, encryption, cache retention, auto-download, metered network and background preferences. ### Direct playback range handover

The direct reader uses one elevated demand interval with a 512 KiB cache probe and a 2 MiB maximum window. It replenishes after advancing 512 KiB in an active interval when the new tail is missing. A seek retains an interval that covers its probe and drops a disjoint interval if the new probe is already cached. Both packet reads and prefetch ranges are clipped at the known file size. EOF and reader disposal release the reader's subscription.

MediaBox queues range registration and removal on the same data queue. Its file context unions requests by priority and keeps the same pending fetch as long as some materialized demand remains. For an overlapping handover, register the replacement and then dispose the previous subscriber. Shared work stays active and the multipart layer excludes cached and in-flight parts. For a disjoint jump, dispose the old subscriber before registering the new one. The pinned multipart planners retain existing in-flight parts when required intervals change, so a disjoint handover that keeps the old task alive can preserve obsolete work. If other subscribers keep that task alive, they continue to own their demand. Verify both orderings in a lifecycle fixture when the pinned dependencies can run. [Pinned MediaBox file context](https://github.com/TelegramMessenger/Telegram-iOS/blob/24638bc69bd083981b178dd1e7f921eebbf7fc46/submodules/Postbox/Sources/MediaBoxFileContextV2Impl.swift#L177-L218) · [Pending fetch update](https://github.com/TelegramMessenger/Telegram-iOS/blob/24638bc69bd083981b178dd1e7f921eebbf7fc46/submodules/Postbox/Sources/MediaBoxFileContextV2Impl.swift#L314-L383)

Each blocked read uses one synchronized outcome. Delivered bytes and cancellation win if they arrive before data-signal completion. Completion without bytes releases the reader with an I/O error. Incomplete cache notifications keep waiting, and a read cannot copy more than the requested byte count. When the active fetch covering the read terminates, inspect the exact requested range through MediaBox. Bytes that are already present can still arrive through the read signal. A missing range ends the read with an I/O error. A stale fetch from a replaced interval has a different completion signal. Verify FFmpeg seek modes and the full failure path with pinned MediaBox and codecs. [Pinned ranged read and completion](https://github.com/TelegramMessenger/Telegram-iOS/blob/24638bc69bd083981b178dd1e7f921eebbf7fc46/submodules/Postbox/Sources/MediaBox.swift#L737-L825)

### Parallel scheduling and adaptation

The pinned core selects FetchV2 for cloud resources by default, subject to user network settings and the upstream kill switch. The macOS app supplies the Rust engine factory. V2 deduplicates byte intervals across priorities and subtracts completed and in-flight parts. With the Rust engine active it starts at six parts, grows or shrinks the window using latency, and adapts master part size from recent throughput. Its configured ceilings are 16 pending master parts and 32 CDN parts per file. The multiplexer separately limits main targets to three requests per worker and four workers per target key. These ceilings operate at different layers. An upper-layer scheduler should only admit files, prioritize demand and bound lookahead, because launching independent requests per player would compete with the existing adaptive transport. CDN responses must be verified before writing, and the existing core handles reference expiry, redirect and fallback. The client must preserve the server's backoff and account policy. [Pinned selector](https://github.com/TelegramMessenger/Telegram-iOS/blob/24638bc69bd083981b178dd1e7f921eebbf7fc46/submodules/TelegramCore/Sources/Network/Network.swift#L747-L752) · [Pinned FetchV2](https://github.com/TelegramMessenger/Telegram-iOS/blob/24638bc69bd083981b178dd1e7f921eebbf7fc46/submodules/TelegramCore/Sources/Network/FetchV2.swift) · [Pinned multiplexer](https://github.com/TelegramMessenger/Telegram-iOS/blob/24638bc69bd083981b178dd1e7f921eebbf7fc46/submodules/TelegramCore/Sources/Network/MultiplexedRequestManager.swift#L209-L215)

The reference C++ change `a44ebb7a18` uses 128 KiB logical parts and varies reader lookahead between 1 and 8 MiB. It falls back to a small window during seeks or unstable measurement, and rotates among ready file tasks. Its observed behavior informs the macOS design. The transport parameters belong to the native core. If later benchmarks show that the fixed rolling window starves a fast link, choose a bounded byte horizon using measured throughput times the request latency and measured consumption times the playback headroom. Apply a low-confidence fallback, hysteresis and a shared foreground budget. Sample bytes delivered over the network and exclude disk reads and overlapping subscribers. Use the existing pinned throughput meter and HLS estimate when those are available at the consumer boundary. A future concurrent Downloads admission policy should reserve playback capacity, rotate among eligible files in the same priority class, keep a progress floor for explicit downloads and give speculative preloads the remainder. Enforce Telegram's per-DC small/large file settings rather than mapping part counts to those quotas. Account for active requests on slow disks, low storage, proxies and simultaneous videos before increasing concurrency.

For an admission experiment, key the work by account, resource and resolved DC. Count one file per active transfer even when several views subscribe. Keep foreground first-frame and seek demand eligible before speculative read-ahead. Admit a ready explicit download whenever its DC and size class have room and playback retains headroom. Return the slot on completion, cancellation or error. On a server wait, set an eligibility deadline for the affected scope and schedule other eligible work. On disk pressure or a growing buffer-write backlog, reduce speculative demand first. Put priority changes, slot ownership and retry deadlines on the scheduler's existing serial queue. Keep multipart retries and connections in TelegramCore so they share its measurements and reference state.

Evaluate file admission separately from the reader window. For the window, compare the fixed 2 MiB baseline with bounded candidates driven by bandwidth-delay product (measured network goodput × RTT) and observed media consumption over the desired startup/seek headroom. Set the minimum and maximum using controlled tests for several simultaneous readers and record the chosen values with the measurements. Cached reads and cancelled attempts do not provide bandwidth samples. Use the current window when samples are sparse or unstable.

### Verification and rollout

Run `sh packages/TelegramMedia/Tests/run-direct-read-ahead-tests.sh` for the standalone XCTest fixtures. Add `--disable-sandbox` in the managed environment if its subprocess sandbox prevents SwiftPM from running. The package target runs the same tests once native dependencies are available.

An uncached 64 MiB sequential-read model with 64 KiB steps measured a peak declared interval of 65.94 MiB in the original unbounded algorithm and 2 MiB in the first rolling implementation. The model issued 32 and 41 subscriptions respectively before the earlier refill change. Overlapping replacements keep the same MediaBox fetch active, so subscription counts and declared bytes do not establish network request counts, transfer volume or observed playback speed.
